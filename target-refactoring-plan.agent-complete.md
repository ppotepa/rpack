# 0. Agent Operating Contract

## 0.1 Read this before touching code

The agent must follow this document as an execution protocol, not as a loose architecture essay.

Default behavior:

```txt
Read this document.
Read only the files named in the current phase.
Make the listed ADD/MODIFY/MOVE/DELETE changes.
Run only the listed validation commands.
Report changed files, tests, remaining debt, and next step.
```

Do not perform broad repo exploration unless the current phase explicitly asks for it.

## 0.2 Primary workflow assumption

The main product workflow is:

```txt
User generates codecat concat of repository.
User gives concat to ChatGPT.
ChatGPT generates an implementation package: preferably package-root, optionally .rpack.
User locally runs rpack to validate, plan, apply, diagnose, repair, and undo.
```

The local tool is primarily a package reader/planner/applier, not primarily a concat-to-package generator.

`create-from-concat` can exist as a developer helper, but it is not the central user story.

## 0.3 Naming rule

Do not call the new package format or architecture “V2”.

Use:

```txt
current rpack
rpack-v1
agent package format
package engine
package-root
operation package
payload package
ChatGPT-generated package
```

Avoid:

```txt
V2
legacy/new
old/new format
v2 manifest
v2 engine
```

## 0.4 Execution response required after each patch

Every implementation response must end with:

```txt
Completed:
Files changed:
Tests run:
Validation result:
Known debt:
Next recommended patch:
```

## 0.5 Cheap-to-expensive validation order

Use this order. Do not run the whole suite after every micro edit.

```txt
1. dotnet build src/Rpack.Core/Rpack.Core.csproj
2. dotnet build src/Rpack.Cli/Rpack.Cli.csproj
3. dotnet test tests/Rpack.Tests/Rpack.Tests.csproj --filter <specific-test-filter>
4. dotnet test
5. Manual CLI smoke for modified command
6. Manual GUI smoke only if Rpack.Open changed
```

Baseline full validation:

```txt
dotnet restore
dotnet build --no-restore
dotnet test --no-build
```

# 1. Hard Product Decisions

## 1.1 What this refactor is

This refactor has two tracks:

```txt
Track A: Split and harden current rpack-v1 patch-applier.
Track B: Add agent package format for ChatGPT-generated package-root/.rpack packages.
```

Track A preserves current behavior.
Track B adds operation/payload package semantics.

## 1.2 What this refactor is not

This is not:

```txt
A Git hosting client.
A CI system.
A general package manager.
A GUI redesign.
A remote package registry.
A semantic merge engine.
A package signing project.
```

## 1.3 Key pain to solve

Current pain:

```txt
One failed check/apply step can block the whole package.
Diagnostics are often raw strings.
CLI and GUI have duplicated semantics.
RpackPackageService owns too much behavior.
```

Target behavior:

```txt
Package is transformed into a plan.
Plan exposes ready, already-applied, fallback-ready, skipped, and conflicting operations.
Safe operations can apply without forcing the user to regenerate the whole package.
Conflicts produce a compact report suitable for ChatGPT repair.
```

# 7. SOLID and IoC Rules

## 7.1 SOLID enforcement

Single responsibility:

```txt
ZIP reading is not manifest validation.
Manifest validation is not Git dry-run.
Patch parsing is not conflict resolution.
GUI rendering is not domain behavior.
Action execution is not apply planning.
State storage is not patch application.
```

Open/closed:

```txt
New validators are new classes.
New package formats are new readers.
New conflict strategies are new resolvers.
Switch statements may only route to handlers.
```

Interface segregation:

Avoid:

```csharp
public interface IPackageService { ... everything ... }
```

Prefer focused interfaces:

```csharp
IPackageReader
IPackageWriter
IManifestReader
IManifestNormalizer
IManifestValidator
IChecksumVerifier
IPatchParser
IPatchTransformer
IPatchSetPreparer
IApplyPlanBuilder
IActionRunner
IRpackStateStore
```

Dependency inversion:

```txt
Use cases depend on abstractions.
Infrastructure implements abstractions.
CLI/GUI compose dependencies.
```

## 7.2 IoC timing

Do not start with IoC.

Correct order:

```txt
1. Add structured result model.
2. Extract package/manifest/checksum components.
3. Extract patch parser/preparer.
4. Introduce ApplyPlan.
5. Extract Git/actions/state.
6. Add use cases.
7. Add IoC composition root.
```

Target composition root:

```csharp
public static class RpackServiceCollectionExtensions
```

## 10.6 Operations schema contract

Required for every operation:

```txt
Id
Kind
Path
ApplyPolicy
Required
```

Required for AddTextFile:

```txt
TargetSha256
PayloadPath
```

Required for ModifyTextFile:

```txt
BaseSha256
TargetSha256

```

Required for DeleteTextFile:

```txt

```

Required for PatchOnly:

```txt

```

Rules:

```txt
Two operations cannot target same Path unless represented as CompositeOperation later.
Path must be safe relative path.
PayloadPath must exist if declared.
PatchPath must exist if declared.
TargetSha256 must equal SHA256(payload bytes) when PayloadPath exists.
DeleteTextFile must not require payload.
AddTextFile should not include BaseSha256 unless enforcing absent-or-known state.
```

## 10.7 Checksums JSON

```json
{
  "manifest.json": "<sha256>",
  "operations.json": "<sha256>",
  "payload/text/<sha256>.txt": "<sha256>",
  "README.md": "<sha256>"
}
```

Rules:

```txt
checksums.json is not required to include itself.
Checksums are over exact entry bytes, not compressed ZIP bytes.
pack-root should generate checksums locally.
If ChatGPT generates final .rpack directly, checksums must still be valid.
```

## 10.8 Hash rules

```txt
SHA256 over exact UTF-8 bytes of payload file.
No ZIP metadata in hash.
Manifest paths use / separator.
Payload text is UTF-8 without BOM unless binary payload is explicitly used later.
Do not normalize line endings during hash verification.
```

Codecat base hash rule:

```txt
Prefer sha256 declared in <<<FILE ... sha256="...">>> metadata.
If missing, hash exact content block according to codecat parser behavior.
```

## 11.4 PlanAddTextFile pseudocode

```txt
Input: operation, target file state, package payload store

if path unsafe:
  ConflictUnsafePath

if payload missing:
  Unsupported / agent.payload-missing

if TargetSha256 != hash(payload):
  Unsupported / agent.payload-hash-mismatch

if target file exists:
  if target sha == TargetSha256:
    AlreadyApplied, method Skip
  else:
    ConflictExistingDifferentFile
else:
  if ApplyPolicy allows payload:
    ReadyWithPayload, method Payload
  else if PatchPath exists and patch dry-run succeeds:
    ReadyWithPatch, method Patch
  else:
    ConflictPatchFailed
```

## 11.5 PlanModifyTextFile pseudocode

```txt
Input: operation, target file state, package payload store

if path unsafe:
  ConflictUnsafePath

if target file missing:
  ConflictMissingFile

if TargetSha256 exists and target sha == TargetSha256:
  AlreadyApplied, method Skip

if BaseSha256 missing:
  Unsupported / manifest.validation-invalid

if target sha != BaseSha256:
  ConflictBaseHashMismatch with ActualTargetSha256

if PatchPath exists and patch dry-run succeeds:
  ReadyWithPatch, method Patch

if PayloadPath exists and payload hash == TargetSha256 and policy allows payload:
  ReadyWithPayloadFallback or ReadyWithPayload, method Payload

else:
  ConflictPatchFailed or agent.payload-missing
```

## 11.6 PlanDeleteTextFile pseudocode

```txt
if path unsafe:
  ConflictUnsafePath

if target file missing:
  AlreadyApplied, method Skip

if BaseSha256 missing:
  Unsupported

if target sha != BaseSha256:
  ConflictBaseHashMismatch

if PatchPath exists and patch dry-run succeeds:
  ReadyWithPatch, method Patch
else:
  ReadyWithPayload, method Delete
```

## 11.7 PlanPatchOnly pseudocode

```txt
if PatchPath missing:
  Unsupported

if patch entry missing:
  package.entry-missing

if patch dry-run succeeds:
  ReadyWithPatch
else:
  ConflictPatchFailed with raw Git details
```

# 12. Agent Package Apply Algorithms

## 12.1 ApplyAddPayload

```txt
Before apply:
  verify path safe
  verify payload exists
  verify payload hash equals TargetSha256
  verify target file absent or already equals TargetSha256
  write journal backup record with ExistedBefore=false

Apply:
  create parent directory
  write payload bytes
  verify resulting hash == TargetSha256

Failure:
  restore from journal if partial write occurred
```

## 12.2 ApplyModifyPayload

```txt
Before apply:
  verify path safe
  verify target exists
  verify current target hash == BaseSha256
  verify payload hash == TargetSha256
  backup original file to journal

Apply:
  overwrite target file with payload bytes
  verify resulting hash == TargetSha256

Failure:
  restore backup
```

## 12.3 ApplyDelete

```txt
Before apply:
  verify path safe
  if file absent -> AlreadyApplied
  verify current target hash == BaseSha256
  backup original file to journal

Apply:
  delete file

Failure:
  restore backup
```

## 12.4 ApplyPatch

```txt
Before apply:
  verify patch entry exists
  verify patch dry-run still succeeds or plan freshness validates
  backup changed files if operation-level journal supports it

Apply:
  run git apply

Failure:
  reverse already-applied patches where possible
  record failure issue
```

## 12.5 SkipAlreadyApplied

```txt
No filesystem change.
Record operation as AlreadyApplied in report.
Do not create backup.
```

## 12.6 Plan freshness

Before applying a saved/generated plan:

```txt
Recheck target hashes for selected operations.
If any selected operation changed since plan, rebuild plan or fail with stale plan issue.
```

## 13.3 Undo algorithm

```txt
Read latest journal.
For each operation in reverse order:
  if ExistedBefore and backup exists:
    restore backup
  if ExistedBefore is false and target exists:
    delete target
  if backup missing:
    record state.backup-missing and stop unless --force
Mark journal undone.
```

## 13.4 Undo safety

If target file changed after apply:

```txt
Default: fail with state.target-changed-after-apply.
With --force: restore/delete anyway.
```

# 14. Package-root Packer Algorithm

Target command:

```txt
rpack pack-root <package-root> -o <package.rpack>
```

Algorithm:

```txt
1. Resolve package-root full path.
2. Validate package-root exists and is directory.
3. Read manifest.json as raw JSON.
4. Validate manifest required fields.
5. Read operations.json from OperationsPath.
6. Validate all operation paths are safe relative paths.
7. Validate every PayloadPath exists under package-root.
8. Validate every PatchPath exists when declared.
9. For each payload file:
   - read exact bytes
   - calculate SHA256
   - compare with TargetSha256 for referencing operations
10. Reject duplicate operation ids.
11. Reject duplicate operation paths unless future composite support is implemented.
12. Build sorted archive entry list.
13. Write deterministic ZIP entries using / separators.
14. Generate checksums.json over all entries except checksums.json.
15. Add checksums.json as final entry.
16. Reopen written .rpack and verify checksums.
17. Return package path and summary.
```

Deterministic sort order:

```txt
manifest.json
operations.json
metadata/*
payload/*
patches/*
diagnostics/*
README.md
checksums.json last
```

Validation failures must not throw for expected errors; return structured issues.

# 17. Repair Flow

## 17.1 User flow

```txt
1. User applies package partially.
2. Some operations conflict.
3. User runs: rpack diagnose package.rpack repo --llm --conflicts
4. User gives conflict report to ChatGPT.
5. ChatGPT generates repair package-root.
6. User runs pack-root and apply on repair package.
7. User optionally runs apply-remaining on original package.
```

## 17.2 Repair manifest extension

```json
{
  "Format": "rpack-agent-package",
  "SchemaVersion": "1.0",
  "Id": "repair-20260614-0001",
  "Title": "Repair for op-0004",
  "RepairsPackageId": "agent-20260614-0001",
  "RepairsOperations": ["op-0004"]
}
```

## 17.3 Repair semantics

```txt
A repair package does not mutate original package.
A repair package can supersede conflicted operations by path.
Journal should link repair package id to original package id.
apply-remaining should consider already-applied files and repair-applied files.
```

# 18. Security and Lint Rules

## 18.1 Archive path safety

Reject archive entry path if:

```txt
empty
absolute
contains ..
contains drive letter
starts with /
starts with \
contains backtracking segment
```

## 18.2 Target path safety

Reject target path if:

```txt
empty
absolute
contains :
contains . segment
contains .. segment
escapes repository root after full path normalization
```

## 18.3 Forbidden paths

Error by default:

```txt
.env
.key
.pem
```

Warn or error depending profile:

```txt
logs/
artifacts/
release/
bin/
obj/
.vs/
.idea/
.pdb
.exe
.dll
.rpack
.user
.suo
```

## 18.4 Secret marker scan

Scan added patch lines and text payloads for:

```txt
BEGIN PRIVATE KEY
api_key
apikey
secret
token
password
```

## 18.5 Network action scan

Warn/block action content containing:

```txt
Invoke-WebRequest
curl
wget

Start-BitsTransfer
```
